# Whispdows NPU acceleration options

**Scope:** Windows desktop, .NET 10 x64 WPF, official/first-party sources only. **Research date:** 2026-08-01.

## Executive conclusion

The best strategic path is **Windows ML + ONNX Runtime behind a new optional transcription backend**, while retaining the current Whisper.net backend as the default/fallback. Windows ML is the Microsoft-supported ONNX Runtime distribution for Windows, exposes C# APIs, and currently maps hardware-optimized providers to Intel OpenVINO, Qualcomm QNN, and AMD VitisAI. It supports x64 and ARM64, but hardware-optimized NPU providers require Windows 11 24H2 (build 26100) or later plus compatible drivers. Sources: [Windows ML overview](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview), [hardware-to-EP mapping](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/accelerate-ai-models), [supported EPs and requirements](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers).

This is not a drop-in acceleration switch for the repository. Whispdows currently uses Whisper.net/whisper.cpp with a GGML model; Windows ML/ONNX Runtime requires an ONNX model. An ONNX Whisper encoder/decoder pipeline must therefore be validated separately, and the existing GGML path should remain available until end-to-end accuracy, latency, and power are proven.

## Repository baseline

- [`Whispdows.csproj`](../src/Whispdows/Whispdows.csproj) targets `net10.0-windows`, WPF, and x64; it references `Whisper.net` and `Whisper.net.Runtime` 1.9.1 and ships `models/ggml-small.en.bin`.
- [`Transcribers.cs`](../src/Whispdows/Transcribers.cs) creates a `WhisperFactory` from the GGML file and only configures language/CPU thread count. There is no ONNX Runtime seam today.
- [`Build-Release.ps1`](../scripts/Build-Release.ps1) publishes self-contained `win-x64`, non-single-file output and validates Whisper native DLLs. [`Whispdows.iss`](../installer/Whispdows.iss) installs x64-compatible Windows only.
- [`OllamaTextCleaner.cs`](../src/Whispdows/OllamaTextCleaner.cs) treats Ollama as a loopback OpenAI-compatible text-cleanup service, not as the transcription engine.

## Compatibility findings

### Whisper and ONNX Runtime

The official OpenAI Whisper implementation downloads PyTorch `.pt` checkpoints and implements the model in PyTorch ([model loader](https://github.com/openai/whisper/blob/main/whisper/__init__.py), [model implementation](https://github.com/openai/whisper/blob/main/whisper/model.py)). Whisper.net uses GGML models ([Whisper.net model/runtime documentation](https://github.com/sandrohanea/whisper.net)), and whisper.cpp's OpenVINO flow generates a separate encoder IR alongside the GGML model ([whisper.cpp OpenVINO documentation](https://github.com/ggml-org/whisper.cpp)).

Windows ML is an ONNX Runtime path. Therefore, moving Whispdows' transcription to Windows ML means supplying a compatible ONNX Whisper pipeline and an adapter that owns tokenization, audio features, encoder/decoder execution, and fallback behavior. This is an inference from the documented model formats and runtimes, not an official claim that a particular ONNX Whisper export will work.

The hard part is the decoder: QNN HTP requires quantized, fixed-shape graphs and supports only a subset of ONNX operators; unsupported nodes may need CPU fallback ([QNN EP requirements](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)). AMD VitisAI partitions supported subgraphs to the NPU and the remainder to CPU ([Ryzen AI deployment](https://ryzenai.docs.amd.com/en/latest/modelrun.html)). OpenVINO supports NPU execution, shape bounds, and compiled-model caching ([OpenVINO EP](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html)). These facts make an encoder-only win plausible, but do not establish full autoregressive Whisper acceleration.

### Ollama

Ollama remains a reasonable optional local cleanup service because its OpenAI-compatible `/v1/chat/completions` API matches the existing integration ([official API compatibility](https://docs.ollama.com/api/openai-compatibility)). Its Windows runtime is documented as a native Windows app with NVIDIA and AMD Radeon GPU support ([Windows documentation](https://docs.ollama.com/windows)); the hardware page describes CUDA/ROCm/Vulkan GPU paths, not NPU execution ([hardware support](https://docs.ollama.com/gpu)). The official source also says Windows ARM currently has no additional acceleration libraries ([Ollama Windows development notes](https://github.com/ollama/ollama/blob/main/docs/development.md)). Treat Ollama as GPU/CPU-only for this investigation; do not promise NPU use or couple Whisper acceleration to it.

## .NET 10/WPF packaging implications

1. **Windows ML is compatible with this framework generation.** Microsoft documents .NET 8 or greater and C# support, so `net10.0-windows` is in range. A WPF/unpackaged sample exists in the official Windows ML sample inventory ([samples](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/samples)).
2. **Keep the current folder-based, self-contained shape.** For an unpackaged Inno Setup release, start with the self-contained `Microsoft.Windows.AI.MachineLearning` (or `Microsoft.WindowsAppSDK.ML`) package. Microsoft says this adds roughly 41 MB for the Windows ML runtime; do not add `Microsoft.WindowsAppSDK.Runtime` or the main Windows App SDK package unless intentionally switching to framework-dependent deployment ([deployment guidance](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/distributing-your-app)).
3. **The runtime and vendor EPs are separate.** The base Windows ML runtime includes ORT/DirectML, while QNN, OpenVINO, and VitisAI are acquired through `ExecutionProviderCatalog` or bundled separately. If downloads are enabled, show progress/consent and handle failure; first-run EP installation and model compilation can take substantial time ([install/register EPs](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/initialize-execution-providers), [selection and C# API](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/select-execution-providers)).
4. **Use RID-specific artifacts.** `.NET` RIDs select native assets ([RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)). Keep `win-x64` for Intel/AMD first. Qualcomm NPU inference requires a separate ARM64 build; an x64 process cannot load ARM64 QNN native libraries. Do not put ARM64 DLLs into the current x64 installer.
5. **Preserve native DLLs and caches as files.** The current non-single-file publish is a good default for Whisper/ORT native libraries, model files, and provider discovery. Store writable compiled-model/provider caches under `%LOCALAPPDATA%\Whispdows`, not the installed program directory. If single-file publishing is considered later, account for native-library extraction and path behavior ([single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)).
6. **Retain a CPU/GGML fallback.** Gate the NPU path on OS build, detected EP/device, model compatibility, driver readiness, and successful session creation. The application should continue to work offline and on Windows versions below 24H2.

## Recommended repository path

1. **Do a bounded proof harness first, outside production source.** Use .NET 10 C# + Windows ML/ORT to enumerate NPU devices and run a fixed-shape ONNX Whisper candidate. Test Intel `OpenVINOExecutionProvider` on an Intel Core Ultra system and AMD `VitisAIExecutionProvider` on a Ryzen AI system; test QNN only in a separate Windows ARM64 build. Measure cold session creation, warm real-time factor, CPU fallback percentage, power, and transcription accuracy. A provider being listed is not proof that the Whisper decoder is accelerated.
2. **If the harness passes, add an `ITranscriber` implementation rather than replacing `WhisperCppTranscriber`.** Ship the ONNX assets and Windows ML setup as an opt-in backend, retain `ggml-small.en.bin` for universal fallback, and make explicit provider selection plus fallback observable in logs/settings.
3. **Use Windows ML's catalog as the production abstraction.** It avoids hard-coding three vendor SDKs and can acquire certified EPs for Intel/Qualcomm/AMD; explicitly enumerate/select the NPU device first, then fall back to CPU. Add a user-visible “download accelerator” step rather than silently downloading vendor binaries during dictation.
4. **Release x64 first.** That covers the repository's current installer and the most practical Intel/AMD NPU targets. Add a separately tested `win-arm64` artifact only if Qualcomm Snapdragon NPU support becomes a product requirement.
5. **Use Whisper.net OpenVINO only as an interim Intel experiment.** It is the smallest change to the current GGML stack, but official documentation does not establish full Whisper NPU acceleration; it should not become the cross-vendor architecture.

## Confidence and limitations

- **High confidence:** Windows ML's current EP list, Windows 11 24H2 requirement, C# APIs, deployment modes, QNN Windows ARM64 inference constraint, AMD VitisAI Windows AMD64 support, and Ollama's documented Windows GPU/ARM behavior.
- **Medium confidence:** Whisper.net OpenVINO is a practical Intel integration point; its official sample and upstream whisper.cpp docs document the encoder path, but not a production Intel-NPU Whisper configuration.
- **Low/unknown until tested:** end-to-end ONNX Whisper decoder coverage, quantization quality, real-time factor, power savings, and whether a chosen export partitions usefully on each NPU. No official source found in this bounded investigation provides a Whisper-on-Windows-NPU benchmark for Whispdows' model.
- Driver versions, model licenses, vendor EP licenses, and Windows Update servicing can change; pin and test the exact Windows ML/ORT package and model artifacts used for each release.
